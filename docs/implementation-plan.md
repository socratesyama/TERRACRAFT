## 2. 設計原則

1. **決定論**：同じ seed と同じ入力列から、必ず同じ世界ができる。`Math.random` は使わず、自作PRNG（mulberry32）を使う。反復順序は固定する。
2. **世界の所有者はWorkerだけ**：メインスレッドは読み取り専用のスナップショットを受け取るだけにする。
3. **システムは純粋に近い関数**：`(world, params, rng) => void`。副作用は World の配列だけ。
4. **保存則を検証する**：水量の総和、土砂の総和をテストで追跡する。
5. **原因を記録する**：すべてのシステムが `WorldEvent` を発行し、「何をしたか」と「何が起きたか」を因果ログに結ぶ。
6. **段階的に劣化する**：128² → 192² → 256² の品質切替と、フレーム予算超過時の間引きを最初から組み込む。

## 4. データモデル詳細

### 4.1 スケール

統計の「km」「m」を実計算にするため、物理スケールを固定します。

| 項目 | 値 |
| --- | --- |
| グリッド | 128 / 192（標準） / 256 |

### 4.2 一次状態と派生状態

保存・継続が必要な**一次状態**と、いつでも再計算できる**派生状態**を分けます。派生状態は dirty フラグが立ったときだけ再計算します。

| 区分 | 配列 | 型 | 説明 |
| --- | --- | --- | --- |
| 一次 | `height` | Float32 | 地表標高 0〜1（水面は含まない） |
| 一次 | `fixed` | Uint8 | 等高線で拘束されたセル |
| 一次 | `sediment` | Float32 | 輸送中の土砂 |
| 一次 | `vegetation` | Float32 | 植生密度 0〜1 |
| 一次 | `population` | Float32 | 人口 |
| 一次 | `landUse` | Uint8 | 0:なし 1:農地 2:村 3:町 4:都市 5:港 |
| 一次 | `road` | Float32 | 道路の強さ |
| 派生 | `flowDir` | Uint8 | D8方向 0〜7、255は出口 |
| 派生 | `flowAcc` | Float32 | 流量累積（上流の降水量の総和） |
| 派生 | `lakeDepth` | Float32 | 窪地の充填深（正なら湖） |
| 派生 | `slope` | Float32 | 勾配 |
| 派生 | `temperature` `moisture` `sunlight` | Float32 | 気候場 |
| 派生 | `biome` | Uint8 | 分類結果 |
| 派生 | `distWater` | Float32 | 最寄りの水域までの距離 |

```ts
  Climate = 1 << 1,  // 気温・水分・バイオームを再計算

```

### 4.3 地形生成の確定仕様

マスタープラン§6のIDW方式を、次の流れに置き換えます。

1. **ラスタライズ**：線分をBresenhamで走査し、`width` の半径で `height` を書き込む。書き込んだセルは `fixed = 1`。重なったセルは平均。
2. **初期推定**：固定セルの標高を、最寄り固定セルから伝播（多始点の幅優先走査）して全セルに初期値を与える。
3. **制約付きラプラス緩和**：固定セルを境界条件として、非固定セルを4近傍平均へ反復（Gauss-Seidel、128²で約200反復、192²で約300反復）。自然に滑らかな曲面になり、尾根と谷が等高線から素直に導かれる。
4. **ノイズ**：ridged fBm（4〜5オクターブ）を加える。振幅は `amp = A × smoothstep(0, R, 固定セルまでの距離)` で変調し、等高線付近の標高が崩れないようにする。
5. **制約の再適用**：固定セルを元の標高へ戻し、3×3平滑を1〜2回。
6. **範囲正規化**：0〜1にクランプ。

**受け入れ基準**：等高線上の標高誤差が0.01以内／同じ seed で配列のハッシュが一致／192²の生成が1秒以内。

## 5. 水文エンジン

### 5.1 二層構造

| 層 | 役割 | 性質 |
| --- | --- | --- |
| A：定常水文 | 川・湖・流量・流向を決める | 派生状態。`Dirty.Height` のときだけ再計算。物理と生態に影響する |
| B：動的表面水 | 雨粒・川が伸びるアニメ・水面の揺れ | 見た目専用。保存せず、物理に影響させない |

「雨を降らせる」ボタンは、層Aの結果を層Bで時間をかけて見せる演出です。計算は即座に終わるので、60FPSを維持したまま因果が伝わります。

### 5.2 パイプライン

1. **出口の決定**：`height < seaLevel` のセル、および `edgeMode='sea'` なら外周セル。出口が1つもない場合は、最も低い外周セルを強制的に出口にする。
2. **Priority-Flood**：出口から標高の低い順に展開し、窪地を充填した標高 `filled` と、展開順 `order` を得る。
3. **流向（D8）**：展開時に「そのセルを発見した親セルの方向」を `flowDir` とする。平坦部や湖の中でも必ず出口へ向かう。
4. **降水から流出へ**：`runoff[i] = precip[i] × (1 − infiltration(vegetation[i]))`。降水は §7.3 の降水分布を使う（雨陰の側は川が細くなる）。
5. **流量累積**：`order` の**逆順**（上流から下流）に処理し、`flowAcc` を受け手へ加算する。ソートは不要。
6. **湖**：`lakeDepth = filled − height` が閾値（初期値0.002）を超えるセル。
7. **川**：`flowAcc ≥ riverThreshold` かつ湖・海でないセル。

```ts
const DX = [1, 1, 0, -1, -1, -1, 0, 1];
const DY = [0, 1, 1, 1, 0, -1, -1, -1];   // 奇数番号が斜め
const EPS = 1e-5;                          // 平坦部にも勾配を与える

export function hydrology(w: World, order: Int32Array): number {
  const { size } = w;
  const { height } = w.primary;
  const { filled, flowDir, flowAcc, lakeDepth, runoff } = w.derived;
  const heap = new MinHeap(size * size);
  const seen = new Uint8Array(size * size);
  let k = 0;

  for (let i = 0; i < height.length; i++) {
    if (isOutlet(w, i)) {
      filled[i] = height[i];
      flowDir[i] = 255;
      seen[i] = 1;
      heap.push(i, filled[i]);
    }
  }
  while (heap.size > 0) {
    const c = heap.pop();
    order[k++] = c;
    const cx = c % size;
    const cy = (c / size) | 0;
    for (let d = 0; d < 8; d++) {
      const nx = cx + DX[d];
      const ny = cy + DY[d];
      if (nx < 0 || ny < 0 || nx >= size || ny >= size) continue;
      const nb = ny * size + nx;
      if (seen[nb]) continue;
      seen[nb] = 1;
      filled[nb] = Math.max(height[nb], filled[c] + EPS);
      flowDir[nb] = (d + 4) & 7;            // nb から c へ向かう方向
      heap.push(nb, filled[nb]);
    }
  }

  flowAcc.set(runoff);
  for (let j = k - 1; j >= 0; j--) {        // 上流 → 下流
    const c = order[j];
    const d = flowDir[c];
    if (d === 255) continue;
    const r = (((c / size) | 0) + DY[d]) * size + (c % size) + DX[d];
    flowAcc[r] += flowAcc[c];
  }
  for (let i = 0; i < height.length; i++) {
    lakeDepth[i] = Math.max(0, filled[i] - height[i]);
  }
  return k;   // 到達できたセル数。size*size 未満なら孤立領域あり
}
```

同点の標高では挿入順で取り出すようヒープを実装し、決定論を保ちます。

### 5.3 「川が伸びる」演出

`order` の逆順パスで、各セルの「最も遠い源流からの距離」`headDist` も求めます。表示時刻 `t` に対して `headDist × speed ≤ t` のセルだけを川として描くと、源流から下流へ川が伸びていきます。

### 5.4 描画に渡す水面

| 場所 | 水面の高さ |
| --- | --- |
| 海 | `seaLevel` |
| 湖 | `filled[i]` |
| 川 | `height[i] + riverDepth(flowAcc[i])`（川幅は `log(1 + acc / threshold) × k`） |

### 5.5 コストと検証

Priority-Flood は O(N log N) です。192² は約3.7万セルなので、10ms以内を目標にし、**実測で確認**します（Phase 2 の最初に計測）。検証する性質は次のとおりです。

- 出口へ到達した流量の総和 ＝ 全セルの流出量の総和（質量保存）
- 下流の `flowAcc` は上流以上
- すり鉢状の地形で、中心に湖ができる
- 川が通るセルに、下り方向の経路が必ず存在する

## 6. 侵食エンジン

### 6.1 河川侵食（Stream Power）

```text
E = K × A^m × S^n    （A：流量累積、S：流向方向の勾配、m=0.5、n=1）
```

陽的に解くと、時間刻みを大きくしたときに発散します。そこで **n=1 の陰的解法**（Braun & Willett 2013）を使い、刻みに依存せず安定させます。出口側から順に処理するため、`order` の**正順**を使います。

```text
h_new[c] = (h[c] + F × h_new[受け手]) / (1 + F)
F = K × dt × A^m / 距離       （斜めは距離を √2 にする）
```

```ts
export function streamPower(w: World, order: Int32Array, n: number, dt: number): void {
  const { size } = w;
  const { height, vegetation, sediment } = w.primary;
  const { flowDir, flowAcc, lakeDepth } = w.derived;
  const { K, M } = w.params.erosion;
  for (let j = 0; j < n; j++) {
    const c = order[j];
    const d = flowDir[c];
    if (d === 255 || lakeDepth[c] > 0.002) continue;      // 湖の中では削らない
    const r = (((c / size) | 0) + DY[d]) * size + (c % size) + DX[d];
    const kEff = K * (1 - 0.8 * vegetation[c]);            // 植生が守る
    const f = (kEff * dt * Math.pow(flowAcc[c], M)) / ((d & 1) ? 1.4142 : 1);
    const next = (height[c] + f * height[r]) / (1 + f);
    const removed = Math.max(0, height[c] - next);
    height[c] = next;
    sediment[c] += removed;                                // 削った量は土砂になる
  }
}
```

植生の項により、伐採で侵食が増え、植林で抑えられます。マスタープランの「伐採→侵食増加」が、追加のルールなしで成立します。

### 6.2 土砂輸送と堆積

`order` の**逆順**（上流から下流）で、土砂を運びながら、運搬能力を超えた分を堆積させます。

```ts
export function transport(w: World, order: Int32Array, n: number): number {
  // 戻り値：海へ流出した土砂量（保存則の検証用）
  const { size } = w;
  const { height, sediment } = w.primary;
  const { flowDir, flowAcc, slope } = w.derived;
  const { Kc, M, depositRate } = w.params.erosion;
  let exported = 0;
  for (let j = n - 1; j >= 0; j--) {
    const c = order[j];
    let load = sediment[c];
    const cap = Kc * Math.pow(flowAcc[c], M) * slope[c];
    if (load > cap) {
      const dep = (load - cap) * depositRate;
      height[c] += dep;
      load -= dep;
    }
    sediment[c] = 0;
    const d = flowDir[c];
    if (d === 255) { exported += load; continue; }
    const r = (((c / size) | 0) + DY[d]) * size + (c % size) + DX[d];
    sediment[r] += load;
  }
  return exported;
}
```

河口では、流量が大きいまま勾配が小さくなり、運搬能力が落ちて土砂が堆積します。**三角州はこの式から自然に現れます**。

### 6.3 斜面崩壊（熱的侵食）

隣接セルとの実勾配が安息角（初期値35°）を超えたとき、超過分の半分を低い側へ移します。順序依存を避けるため、差分配列に書いてから一括で適用します。1 tick あたり2〜3パスです。

### 6.4 実行頻度

侵食のたびに水文を再計算すると重いため、**4 tick に1回**まとめて適用し、`dt=4` を渡します（陰的解法なので安定）。

**保存則テスト**：削った総量 ＝ 堆積した総量 ＋ 海へ出た総量。

## 7. 気候・生態系エンジン

### 7.1 依存関係

```text
高さ → 気温・風・降水分布 → 水文（流量・湖） → 水分 → 植生 → バイオーム
                                   ↑                         ↓
                             侵食（植生が抑制）←──────────────┘
```

循環は「前の tick の植生」を使うことで切り、1 tick の中は一方向に計算します。

### 7.2 気温

```text
T = T0 − latGradient × (y / size) − 6.5 × 標高(km) + 海の緩和 + temperatureBias + 季節振幅 × sin(season)
海の緩和 = (T海 − T) × 0.2 × LUT(海からの距離)
```

- 6.5℃/km は標準的な気温減率です。
- 指数関数は、整数距離0〜64の**事前計算LUT**に置き換えます（ブラウザ差による決定論の崩れを避ける）。
- マスタープランのように水量・植生を気温へ足すと正帰還になるため、植生による冷却は −0.5℃×植生 を平滑化後に加える程度にとどめます。

### 7.3 風と降水（地形性降雨・雨陰）

風向は45°刻みの8方向とし、風上の縁から風下へ、行（または斜めの線）ごとに湿った空気を運びます。

```ts
for (const line of windwardLines(size, windDir)) {
  let q = humidity0;                       // 空気中の水蒸気量
  let prev = -1;
  for (const c of line) {
    if (isOcean(c) || lakeDepth[c] > 0.002) q = Math.min(qMax, q + evapGain);
    const lift = prev < 0 ? 0 : Math.max(0, height[c] - height[prev]) * liftK;
    const rain = Math.min(q, q * (baseRainFrac + lift));   // 上昇で凝結
    precip[c] = rain;
    q -= rain;                                              // 風下側は乾く＝雨陰
    prev = c;
  }
}
```

**最終降水量** ＝ この分布 × `rainfallScale`（UIの降水スライダー）。これを水文の入力（`runoff`）と水分の計算の両方に使います。

### 7.4 水分と日照

```text
moisture = clamp01( 降水 × k1 + 川・湖の近さボーナス × k2 )  → 3×3平滑化を2回
sunlight = 0.4 + 0.6 × max(0, dot(法線, 太陽方向))        （季節で太陽方向を変える）
```

川や湖の近くは水分が増え、日当たりの悪い斜面は成長が遅くなります。

### 7.5 バイオーム（気候が決める潜在植生）

上から順に判定します。

| 順 | 条件 | バイオーム |
| --- | --- | --- |
| 1 | 海・湖・川のセル | 水域 |
| 2 | `T < 0℃` または 標高が雪線超 | 高山（雪） |
| 3 | 海から1.5セル以内で `height < seaLevel + 0.03` | 海岸 |
| 4 | 平坦かつ `flowAcc` 大かつ `moisture > 0.7` かつ湖でない | 湿地 |
| 5 | `moisture ≥ 0.55` | 森林 |
| 6 | `moisture ≥ 0.25` | 草原 |
| 7 | それ以外 | 砂漠 |

しきい値付近でのちらつきを防ぐため、**ヒステリシス**（±0.03）を設け、前回のバイオームを維持します。

### 7.6 植生ダイナミクス

マスタープランの成長式を、**収容力 `Kcap`** として残します。

```text
Kcap = clamp01( moisture × 0.5 + sunlight × 0.3 + 温度適合度 × 0.2 ) × 傾斜ペナルティ
```

```ts
export function growVegetation(w: World, dt: number): void {
  const { vegetation: V } = w.primary;
  const { r, seed, decay } = w.params.vegetation;
  for (let i = 0; i < V.length; i++) {
    if (!isLand(w, i)) { V[i] = 0; continue; }
    const kcap = capacity(w, i);
    const neighbor = meanNeighbor(V, i, w.size);              // 種子の供給
    let v = V[i];
    if (kcap > 0.02) {
      v += dt * (r * v * (1 - v / kcap) + seed * neighbor);
    }
    if (v > kcap) v -= decay * (v - kcap);                    // 環境が悪化したら枯れる
    V[i] = Math.min(1, Math.max(0, v));
  }
}
```

- **砂漠化**：降水を減らす → `Kcap` が下がる → 植生が減る → 侵食が増える。個別のルールを書かずに起きます。
- **森林回復**：周囲の植生が種子を供給し、水分があれば広がります。
- 初期植生は、水分が0.2を超える陸セルに0.02を置き、成長が始められるようにします。
- 見た目は「潜在バイオーム」と「実際の植生密度」の両方で決めます（森林の気候でも、伐採直後は裸地に見える）。

## 8. 集落・文明エンジン

### 8.1 事前計算（派生状態）

| 配列 | 計算 | 再計算の条件 |
| --- | --- | --- |
| `distWater` | 川・湖・海からの距離変換（chamfer 3-4、2パスで O(N)） | `Dirty.Water` |
| `hand` | 最寄りの川までの比高（下流から順に `hand[c] = h[c] − h[受け手] + hand[受け手]`、川は0） | `Dirty.Height` |
| `drainAcc` | そのセルが流れ込む川の流量（`order` の正順で伝播） | `Dirty.Height` |
| `floodRisk` | `(1 − clamp01(hand / handSafe)) × clamp01(log(1 + drainAcc) / log(1 + accMax))` | `Dirty.Height` |

### 8.2 居住適性

```text
適性 = 水への近さ × 0.4 + 平地度 × 0.3 + 植生 × 0.2 + 交通 × 0.1 − 洪水リスク × 0.5
水への近さ：川・湖から1〜6セルが最大（水面そのものは除外）。LUTで評価
```

マスタープランの式に洪水リスクを加えたので、「川の近くには住むが、氾濫原の真ん中には住まない」という自然な配置になります。

### 8.3 集落の発生と成長

集落は、セルの属性ではなく**オブジェクトのリスト**として持ちます。`population` と `landUse` の配列は、描画と統計のために、リストからラスタライズします。

```ts
export interface Settlement {
  id: number;
  x: number; y: number;
  pop: number;
  tier: 0 | 1 | 2 | 3;   // 村 / 町 / 都市 / 港町
  foundedTick: number;
  foodBalance: number;
}
```

- **発生**：4 tick ごとに、適性が `spawnThreshold`（初期値0.62）を超え、既存集落から8セル以上離れた候補を、適性で重み付けしたPRNGで選ぶ。初期人口は20。
- **成長**：`dP = r × P × (1 − P / Kc)`。`Kc` は、周辺の農地が生む食料と水供給から決まる。
- **農地の拡大**：人口が増えると半径が広がり、草原を農地へ変える（植生が減り、侵食・水分に影響する）。
- **階層**：人口 ≥ 500 で町、≥ 3,000 で都市。海に接する町以上は港町。
- **移動**：洪水リスクが高い、または `P > Kc` が続くと人口が流出し、次の候補地に新しい集落ができる（「集落が移動する」）。

### 8.4 道路

```text
コスト = 1 + 8 × 傾斜² + 川(橋)6 + 森林1.5 + 既存道路0.3 （湖・海は通行不可）
```

最近傍グラフ＋最小全域木の辺について、Dijkstra で経路を求めます。1 tick あたりの探索ノード数に\*\*予算（4,000）\*\*を設けて、Worker内で分割実行します。経路は、新しい集落ができたときと、経路上の標高が変わったときだけ再計算します。

### 8.5 災害

- **洪水**：降水の急増またはダム決壊時、`stage = k × sqrt(drainAcc) × surge` に対し `max(0, stage − hand)` を浸水深とし、人口を `pop × floodRisk × 0.3` だけ減らす。
- **干ばつ**：水分が下がり、食料が減る。
- **土砂災害**：急斜面で植生が失われたときに発生。

すべての災害が、原因の文字列つきでイベントログに残ります（§9.4）。

### 8.6 受け入れ基準

- 発生地点の `distWater` の平均が、陸全体の平均より小さい
- 山頂・海上・氾濫原の中心には発生しない
- 500 tick 動かしても人口が発散しない（`Kc` で頭打ちになる）

## 9. 干渉ツールと操作ログ

### 9.1 すべての干渉は「Op（純データ）」にする

山を削る、森を切る、ダムを作る、といった操作はすべて `Op` として記録し、`applyOp(world, op)` で世界に適用します。このログが、**Undo/Redo・URL共有・因果ログ・決定論的な再生**の共通の土台になります。ドラッグ1回は1つのOpにまとめ、ログの肥大を防ぎます。

```ts
export type Op =
  | { t: 'contour'; tick: number; stroke: ContourStroke }
  | { t: 'raise';   tick: number; pts: number[]; r: number; amount: number }  // 盛り土(+)/山削り(-)
  | { t: 'forest';  tick: number; pts: number[]; r: number; amount: number }  // 植林(+)/伐採(-)
  | { t: 'dam';     tick: number; a: Vec2; b: Vec2; crest: number }
  | { t: 'fill';    tick: number; pts: number[]; r: number }                  // 埋め立て
  | { t: 'param';   tick: number; key: ParamKey; value: number }              // 降水・気温・風向・海面
  | { t: 'rain';    tick: number; amount: number };                           // 雨イベント
```

### 9.2 ツール別の仕様

| ツール | 変更する一次状態 | 立てる dirty | 因果ログの例 |
| --- | --- | --- | --- |
| 山削り・盛り土 | `height` を `amount × smoothstep(距離)` だけ増減 | `Height` | 「標高を120m下げた → 川の流路が変わり、上流の集水域が180セルから95セルになった」 |
| 伐採・植林 | `vegetation` を増減 | `Climate` | 「森林を伐採した → 侵食係数が上がり、下流に土砂が堆積した」 |
| ダム | 2点を結ぶ線上の `height` を `max(元の標高, 川床 + crest)` にする | `Height` | 「ダムで上流に湖ができ、下流の流量が減った」 |
| 埋め立て | 水域の `height` を `seaLevel + 0.02` に引き上げる | `Height` `Water` | 「入り江を埋め立てた → 港の適地が消えた」 |
| 降水・気温・風向・海面 | `params` を変更 | `Climate` | 「降水量を減らした → 森林率が42%から35%に低下した」 |
| 雨 | 降水イベント（演出） | なし | 「雨が降り、川が形成された」 |

**ダムの扱い**：ダムは高さの壁を作るだけにして、湖は Priority-Flood が自動で作ります。壁の両端は谷壁へ**スナップ**させ、確定前に水文を試走して、湖の予測を半透明で見せます（ドライラン）。

### 9.3 Undo/Redo

Opログと**スナップショットのリング**（直近8個、50 tick ごと＋Op適用直前）で実現します。Undo は、直前のスナップショットへ戻してOpを再適用します。決定論なので結果は一致します。メモリは、192² で一次状態が約1MB × 8 で約8MB です。

### 9.4 イベントログと因果の紐づけ

```ts
export interface WorldEvent {
  tick: number;
  kind: 'op' | 'river' | 'lake' | 'forest' | 'desert' | 'settle' | 'flood' | 'erosion' | 'deposit';
  causeId?: number;      // 原因となったOpの番号
  message: string;       // 日本語のテンプレート
  x?: number; y?: number; // クリックでカメラが移動
}
```

- **検出器**：川の総延長 ±10%、湖の新規・消滅（連結成分で数える）、森林率・砂漠率 ±3pt、新集落・都市昇格、洪水、堆積量の閾値超え。
- **紐づけ**：Opの適用後40 tick のあいだに起きたイベントへ、そのOpの `causeId` を付ける。
- **間引き**：同じ種類のイベントは10 tick に1回まで。
- **UI**：ログをクリックすると、原因のOpの位置を強調し、**変化前後の差分ヒートマップ**（`|after − before|`）を重ねる。これが「因果が見える」の実体です。

## 10. 実行スケジュール

### 10.1 1 tick の構成（192² の予算は目標値。実測で調整）

| 段階 | 内容 | 頻度 | 予算 |
| --- | --- | --- | --- |
| 1 | Op の適用 | 毎 tick の先頭 | 2ms |
| 2 | 気温・降水分布・日照 | `Height`/`Climate` が dirty のとき、または8 tick ごと（季節） | 6ms |
| 3 | 水文 | `Height` が dirty、または降水が変化したとき | 10ms |
| 4 | 侵食・土砂輸送・斜面崩壊 | 4 tick に1回（dt=4） | 8ms |
| 5 | 水分・バイオーム | 2 tick に1回 | 3ms |
| 6 | 植生 | 毎 tick | 2ms |
| 7 | 集落・農地・道路 | 毎 tick（発生は4 tick ごと、道路は探索予算つき） | 2ms |
| 8 | イベント検出・統計 | 毎 tick | 1ms |
| 9 | スナップショットの発行 | 最大10Hz | コピー分 |

平均して 33ms/tick を超えないことを目標にします。マスタープランの「水流1ステップ50ms以内」は、この予算で満たせます。

### 10.2 再生速度

1x ＝ 5 tick/秒を出発点にし、4x・16x まで用意します。Worker が追いつかないときは、速度を自動的に落として表示します。

### 10.3 負荷が高いときの段階的な劣化

直近10 tick の平均が33msを超えたら、侵食の間隔を4→8、植生を毎 tick→2 tick ごとへ広げ、画面に「高速モード」と表示します。**Op の適用は決して飛ばしません。**

### 10.4 Worker のループ

`MessageChannel` で自分自身に次のバッチを予約し、**12msの時間切れ**で一度手を止めて、届いたOpや停止命令を処理します。これで、重い計算の最中でも、山削りの操作が即座に反映されます。

## 11. Worker プロトコル

```ts
export type ToWorker =
  | { type: 'init'; seed: number; size: number; params: WorldParams; ops: Op[]; fastForwardTo?: number }
  | { type: 'op'; op: Op }
  | { type: 'play'; speed: number }
  | { type: 'pause' }
  | { type: 'step'; n: number }
  | { type: 'rewind'; toOpIndex: number }       // Undo
  | { type: 'release'; buffers: ArrayBuffer[] } // 描画済みバッファの返却
  | { type: 'dryRunDam'; a: Vec2; b: Vec2; crest: number };

export type FromWorker =
  | { type: 'ready' }
  | { type: 'snapshot'; tick: number; pack: RenderPack; stats: Stats; events: WorldEvent[] }
  | { type: 'progress'; done: number; total: number }  // 早送り中
  | { type: 'dryRunResult'; lakeMask: Uint8Array }
  | { type: 'error'; message: string };
```

- **RenderPack**：`height`(F32)、`waterSurface`(F32)、`riverAlpha`(U8)、`vegetation`(U8)、`biome`(U8)、レイヤー表示中だけ `temperature`/`moisture`/`erosionDiff`(U8)。192² で約0.4MB、10Hz で約4MB/秒です。
- **バッファプール**：メイン側が描画を終えたら `release` で返し、Worker が再利用する（GCを避ける）。
- **バックプレッシャー**：前のスナップショットが返却されるまで、次を送らない。
- **統計**は Worker 内で集計して送る。メイン側は表示するだけ。
- **エラー**：tick を `try/catch` で囲み、例外時は一時停止して `error` を送る。各 tick の後（開発時のみ）、全配列に NaN と範囲外がないか検査する。
- **プレビュー**：等高線を描いている間は、`terrain.worker` が 64² で低解像度の地形を作り（100msで間引き）、指を離したときに本解像度で確定する。

## 12. 描画設計

### 12.1 構成

| 要素 | 方式 |
| --- | --- |
| 地形 | `PlaneGeometry(size-1, size-1)` ＋ 頂点シェーダが高さテクスチャを読んで変位。頂点＝セルなので `NearestFilter` で正確（浮動小数点テクスチャの線形補間は拡張機能が要るため避ける）。再メッシュ不要 |
| 地形の色 | フラグメントシェーダ：バイオームのLUT ＋ 標高の色 ＋ 陰影（法線は高さテクスチャの差分から）。`uLayer` でレイヤー（気温・降水・侵食など）を切替 |
| 水 | 同じ格子の別メッシュ。`waterSurface` から変位し、深さが0以下は `discard`。浅い→深いで色を変え、法線を流して揺らす。`riverAlpha` ＋ `uReveal`（§5.3）で「川が伸びる」演出 |
| 植生 | `InstancedMesh`（低ポリの木、上限12,000本）。森林かつ植生0.35以上のセルに、セル番号のハッシュでずらして置く。差分があるときだけ1秒に1回更新。草原は色だけで表現 |
| 集落 | 階層ごとの `InstancedMesh`。夜は発光 |
| 道路 | 地形に沿わせたリボン。道路が変わったときだけ再生成 |
| 光 | 太陽（平行光）＋半球光。MVP は影を使わず、傾斜と曲率で擬似的な陰影をつける |
| 後処理 | トーンマッピングとFXAA。夜景のブルームは Phase 6 |

### 12.2 カメラと操作

- 軌道カメラ。極角を制限して、地面の下に潜らないようにする。
- **描画モード**：真上からの視点にして、2Dのキャンバスを重ねる（§13.3）。
- **ブラシ位置**：メッシュへのレイキャストではなく、**高さ配列に対するレイマーチ**で求める（軽い）。
- **デモ用カメラツアー**：島の周りを回るスプライン（Phase 6、説明動画用）。
- `devicePixelRatio` は2まで、モバイルは1.5まで。

### 12.3 描画ループ

`requestAnimationFrame` で回し、新しいスナップショットが届いたときだけテクスチャを更新します。ドローコールは15以下、三角形は192²で約7万です。アンマウント時に、ジオメトリ・マテリアル・テクスチャを必ず `dispose` します。

## 14. URL共有

### 14.1 保存するもの

世界の配列は保存せず、**世界を再現するための入力**だけを保存します。

| 項目 | 内容 |
| --- | --- |
| バージョン | 1バイト。将来の形式変更に備える |
| seed・サイズ | seed は4バイト、サイズは1バイト |
| パラメータ | 降水・気温・風向・侵食率・植生率・海面など。1項目1バイトに量子化 |
| 等高線 | 標高・太さ・点列。最初の点は2バイト、以降は前の点との差分（zigzag の可変長整数） |
| Opログ | 種類・tick・座標・量 |
| 再生位置 | 共有時の tick（2バイト） |
| 検査値 | CRC16 |

圧縮は `CompressionStream('deflate-raw')`、非対応なら fflate。最後に base64url にして `#w=...` に入れます。ハッシュはサーバーへ送られません。

### 14.2 容量の見積もり

等高線30本（間引き後は1本あたり約30バイト）＋ Op 50個（約12バイト）＋ ヘッダ ＝ 約1.5KB。圧縮後に base64 化しても約1,500〜2,000文字で、**目標の8,000文字に大きな余裕**があります（実測で確認）。

- 7,500文字を超えるときは、Douglas–Peucker の許容誤差を広げ、Opの座標精度を落として再エンコードする。それでも超えたら、JSON書き出しを案内する。
- 復号に失敗したら、わかりやすいエラーを出して初期状態へ戻す。

### 14.3 「現在の世界」を開くための早送り

決定論なので、開いた側は seed と入力列から世界を再生します。ただし、200 tick を 33ms/tick で進めると約7秒かかります。次の2つを選べるようにします。

- **設計図のみ**：tick 0 から始める。開いた人が「雨を降らせて」進行を見られる。
- **現在の時点**：早送り（描画なし）で追いつく。進捗バーを出し、上限は300 tick。速度は Phase 6 で実測し、遅ければ早送り時だけ侵食の `dt` を大きくする。

### 14.4 その他の保存

- **自動保存**：`localStorage` に2秒のデバウンスで保存（最新1つ＋手動スロット3つ）。すべて `try/catch` で囲む。
- **スクリーンショット**：レンダラを描画した直後に `canvas.toBlob`。統計パネルを重ねたPNGも作れる（Phase 6）。

### 15.2 性質テスト（必ず守る不変条件）

- **水の保存**：出口へ到達した流量の総和 ＝ 流出量の総和
- **土砂の保存**：削った量 ＝ 堆積した量 ＋ 海へ出た量
- **決定論**：同じ入力から、同じ配列のハッシュ（FNV-1a、量子化後）
- **有限性**：1000 tick の後も、全配列に NaN・Infinity・範囲外がない
- **単調性**：下流の `flowAcc` は上流以上
- **往復**：URLのエンコード → デコード → 再生で、元の世界のハッシュと一致

### 15.3 統合シナリオ

| シナリオ | 検証内容 |
| --- | --- |
| 山を作ると川が流れる | 川のセルが閾値以上あり、すべて出口へつながる |
| 盆地を作ると湖ができる | `lakeDepth > 0` のセルが盆地の内側に連結して存在する |
| 山を削ると流路が変わる | 削った領域で `flowDir` の変化があり、川の総延長が変わる |
| 森を切ると侵食が増える | 同じ地形・同じ tick で、土砂の移動量が増える |
| ダムを作ると湖ができる | 壁の上流側に新しい湖の連結成分が現れ、下流の `flowAcc` が減る |
| 乾燥させると砂漠化する | 降水を下げた後、砂漠率が上がり、植生の平均が下がる |
| URLを開くと同じ世界が復元される | 往復テストと同じ |

### 15.4 ブラウザ間の決定論

ゴールデンのハッシュを Chrome・Firefox・Safari で比べます（Phase 3 で実施）。差が出たら、超越関数（`exp`、`pow`、`sin`）の使用箇所をLUTや整数演算へ置き換えます。

## 21. 国家モード（方針変更）：自然は「神」、プレイヤーは「国」

§1〜§20 は「プレイヤーが神として世界を操作する」前提で書きました。ここでは、**自国と他国（AI）が並び立ち、発展度を比べ合う**形へ設計を切り替えます。水文・侵食・気候・生態系のエンジン（§5〜§8）はそのまま土台として使い、その上に「神アルゴリズム」と「国家層」を載せます。

### 21.1 変更の要旨

| 項目 | これまで | 今回 |
| --- | --- | --- |
| プレイヤーの立場 | 神（地形・雨・気温を操作） | 一国の統治者 |
| 雨・気候・災害 | ユーザーが操作 | **神アルゴリズム**が自動で決める（プレイヤーは触れない） |
| 集落 | 条件を満たすと自動発生 | 国家が建設・発展させる（AIも同じ） |
| 他者 | なし | AI国家 3か国（合計4か国から開始） |
| 目的 | 体験・実験 | 他国と比べて、自国の**発展度**を高める |
| 干渉の結果 | 世界が変わる | 世界が変わり、さらに国ごとの優劣として返ってくる |

**因果の連鎖**は残ります。ただし主役が変わります。

```text
神（自然）が状況を作る → 各国が対応する → 自然が人間の行いに応答する → 発展度に差が出る
```

**この設計の前提（要確認）**

1. 地形は、**ゲーム開始前**に決める（等高線で描く、または seed で生成）。開始後は直接編集できない。山を削るなどは、高コストの「公共事業」としてだけ残す。
2. 時間は、これまでどおりリアルタイム進行（一時停止・倍速あり）。
3. 戦争・貿易・同盟は最初のスコープに入れない。まずは「自然と内政」で勝負する。
4. 国の数は、プレイヤー1＋AI 3。

### 21.2 神アルゴリズム（Nature Director）

雨・気温・風・災害を、seed と tick だけから**決定論的に**決めます。プレイヤーの入力は一切入りません。

| 要素 | 内容 |
| --- | --- |
| 季節 | 年周期の降水・気温の変化 |
| 数年〜数十年の変動 | seed から作った1次元の滑らかなノイズで、豊水期・渇水期、冷夏・暖夏が波のように来る |
| 長期の傾向 | seed ごとに「やや乾燥化」「やや湿潤化」などの傾きを持つ |
| 災害イベント | 豪雨・洪水、干ばつ、森林火災、土砂崩れ。確率は**世界の状態に応じて変わる** |

災害の確率が状態に依存する点が、ゲームとして効きます。たとえば、植生が乏しい斜面では土砂災害の確率が上がり、乾燥した森では火災の確率が上がります。つまり、**人間の行いが災害の確率を変える**ので、神は気まぐれでも不条理ではありません。

```ts
export interface NatureState {
  rainfallScale: number;   // 降水倍率（水文・水分へ渡す）
  tempBias: number;
  windDir: number;         // 0〜7
  events: NatureEvent[];   // この年に発生する災害
  forecast: Forecast[];    // 数年先の予報（精度に限りあり）
}

export function natureStep(world: World, rng: Rng, tick: number): NatureState;
```

- **公平性**：同じ事象は、全国家に同じ物理で作用する。特定の国を狙い撃ちしない。
- **予報**：数年先の降水・災害の確率を、精度に限りをつけて表示する。先を読む判断（備蓄、堤防、灌漑）が戦略になる。AIも同じ精度の予報を使う。
- **再現性**：同じ seed なら同じ天候になる。そのため、「同じ世界で別の戦略を試す」「友だちと同じ条件で競う」ことが、URLだけでできる。
- §9 の `param` と `rain` のOpは、プレイヤー操作ではなく、この関数が決めた値に置き換わる。seed と tick から再計算できるので、Opログへ記録する必要はない。

### 21.3 国家モデル

```ts
export interface Nation {
  id: number;                    // 1..N（0は無主地）
  name: string;
  color: string;
  isPlayer: boolean;
  capital: Vec2;
  personality: Personality;      // AI用：拡張・保全・商業・慎重の重み
  stock: { food: number; wood: number; wealth: number };
  tech: number;                  // 0〜100
  policy: PolicyWeights;
}

// PrimaryFields に追加
owner: Uint8Array;               // 各セルの所属国（0＝無主）
// Settlement に追加
nationId: number;
```

**国境の生成**

1. 各国の首都候補を、居住適性（§8.2）が高い場所から選ぶ。首都どうしは十分に離す。
2. 首都から多始点のDijkstraで領土を広げる。コストは、傾斜と川の横断に高い値を与える。すると、**国境が川や稜線に沿って自然に決まる**。
3. 4か国の「初期ポテンシャル」（領土内の適性の合計）の差が15%以内になるまで、首都を選び直す。比較の前提が公平になる。

**国境線の描画**：`owner` の隣接差から、marching squares で輪郭線を取り、地形に沿わせて国の色で描く。領土の半透明の着色は、レイヤーで切り替える。

**領土の拡張**：最初は、無主地の開拓だけにします。境界のセルを、資源を払って自国にします。

### 21.4 プレイヤーの行動

行動は、すべて資源（食料・木材・富）を消費する `nation_action` のOpとして記録します。地形を直接変える操作は、公共事業に格上げします。

| 行動 | 主な効果 | 自然への応答（因果） |
| --- | --- | --- |
| 農地の開発 | 食料の増加、人口の上限（`Kc`）の上昇 | 植生が減り、侵食が増える |
| 植林・森林保護 | 木材の長期的な増加、侵食の抑制、水分の増加 | 短期の食料・富は伸びにくい |
| ダム・ため池・灌漑 | 干ばつへの耐性、洪水の緩和 | **下流の流量が減る**（他国の干ばつにつながり得る） |
| 堤防・治水 | 洪水の被害の減少 | 氾濫原の利用が進む |
| 道路・港 | 成長の加速、交易路 | 森林の分断、河川の橋 |
| 都市計画 | 人口の上限の上昇、避難所 | 氾濫原への依存が増えるとリスクが上がる |
| 研究 | 農業効率、防災、土木の能力 | なし |
| 領土の開拓 | 領土の拡大 | 国境の摩擦（AIの反応は§21.5） |
| 切土・運河（公共事業） | 地形の変更（高コスト） | 流路・湖・集落適性の変化 |

**上流国と下流国**の関係が、この作品ならではの面白さになります。上流の国がダムで水を貯めると、下流の国は渇水に見舞われます。逆に、上流が森を切ると、下流に土砂と洪水が来ます。世界の物理が、そのまま外交の火種になります（戦争は後回しなので、まずは摩擦として表示します）。

### 21.5 AI国家

**Utility AI**（行動ごとに点数をつけて、一番高いものを選ぶ方式）にします。

```text
点数 = 不足の解消度 × 性格の重み × 費用対効果 − リスク
```

- **不足の解消度**：食料が足りない → 農地・灌漑、洪水リスクが高い → 堤防、森林が減った → 植林、など。
- **性格**：拡張主義・保全重視・商業重視・慎重の重みを、国ごとに seed から決める。国ごとの個性が出る。
- **チートなし**：AIも、プレイヤーと同じコスト・同じ規則・同じ予報を使う。資源のボーナスは、難易度の選択としてだけ用意する。
- **決定論**：国ごとに、`seed XOR nationId` のPRNGを使う。AIの判断は、状態から決まる関数なので、URLにはプレイヤーのOpだけを入れれば再現できる。
- **負荷**：各 tick で1国ずつ順番に判断し、候補は集落周辺からサンプリングした上位K個に絞る。1 tick あたり2ms以内を目標にする。
- **見える化**：AIの行動をイベントログに出す（「北のアルド国が川上にダムを建設した」「南のベル国で干ばつが続いている」）。

### 21.6 発展度（Development Index）

この作品の「勝ち負け」を決める指標です。**規模だけで決めず、持続可能性を重く扱う**のが要点です。

| 指標 | 重み | 中身 |
| --- | --- | --- |
| 人口 | 20 | 人口と、人口の上限に対する余裕 |
| 食料の安定 | 15 | 食料収支、飢饉の少なさ |
| 経済 | 20 | 富、交易路、都市の数 |
| インフラ | 10 | 道路・港・治水の整備率 |
| 環境の健全さ | 15 | 森林率の維持、侵食と堆積の少なさ |
| 災害への強さ | 10 | 被害の小ささ、立ち直りの速さ |
| 技術 | 10 | 研究の水準 |

```text
DI = Σ（重み × clamp01(実績 / 基準値)）      0〜100
```

- **基準値**は、世界の適性の合計などから決める**固定値**にする（他国の成績で動かさない）。ほかの国が伸びても、自国の評価が理由なく下がらないようにするため。
- **二つの見方**を並べる。①絶対値（規模の大きさ）、②ポテンシャル比（実績 ÷ 初期ポテンシャル）。恵まれた土地の国が、必ず勝つ形にならない。
- **持続可能性のペナルティ**：森林率や土壌が一定の線を下回ると、DIに上限がかかる。短期の成長のために森を切り尽くすと、後で効いてくる。
- **集計**：国ごとの値は、`owner` を使った1回のパス（O(N)）で、Worker内で集計する。

### 21.7 画面と比較の見せ方

- **ランキング**：全国のDIの順位と、自国との差。推移の折れ線グラフ。
- **自国のダッシュボード**：DIの内訳（レーダーチャートか棒）、食料・木材・富、今年の災害の予報。
- **比較**：自国と、1位・平均との差を、指標ごとに並べて見せる。「いちばん差が大きいのは、環境の健全さ」のような示唆を1行で出す。
- **イベントログ**：神のイベント、他国の行動、自国の行動を、種類で色分けする。
- **地図**：国境線、領土の着色、首都のマーカー、集落の国色のリング。

### 21.10 検証

- **AIの公平性**：対称な地形で、AI同士を100通りの seed で走らせ、勝率が1/Nから大きくずれない。
- **放置の検証**：何も行動しない自国が、AIの下位になる（行動に意味がある）。
- **健全性**：人口や資源が発散せず、負にならない。
- **神の公平性**：同じ事象は全国家に同じ物理で作用する。同じ seed と同じ行動で同じ結果。
- **国をまたぐ因果**：上流国のダムで、下流国の流量が減り、渇水のイベントが出る。
- **決定論**：プレイヤーのOpだけを入れたURLから、AIを含めて同じ世界が再現される。

- 国ごとの初期ポテンシャルを、完全に揃えるか、差を残して「ハンデ付き」にするか。

## 22. 外交・貿易・戦争（最初から入れる版）

§21.1 の前提3（戦争・貿易・同盟は初期スコープ外）と、§21.9 の削り順、§21.11 の一部は、本章で**置き換え**ます。国どうしの直接のやり取りを、設計の最初から組み込みます。

### 22.1 方針：やり取りの動機は、自然の物理から生まれる

外交・貿易・戦争を、地形・水・気候と切り離したカードゲームにしません。次のように、**自然が動機を作り、人間の行いが自然へ返る**形にします。

| 場面 | 自然がどう関わるか |
| --- | --- |
| 貿易の動機 | 平野は食料、森は木材、山は鉱石を産む。土地ごとの偏りが、補い合う関係を作る |
| 貿易の経路 | 道路・川（下りは安い舟運）・海（港どうし）の輸送コストで決まる |
| 戦争の動機 | 渇水（上流のダム）、食料不足、肥沃な平野、水源、港 |
| 戦いの地形補正 | 高地は守りやすく、川を渡る攻撃は不利。森は守りに有利で、進軍が遅い |
| 戦争が自然へ返す影響 | 焦土作戦で植生が減る。軍需で伐採が増える。**ダム・堤防の破壊で下流が洪水になる** |
| 神の関与 | 干ばつの年は、食料を輸入に頼る国が弱みを握られる。豪雨の年は、進軍が止まる |

### 22.2 国家間の関係と外交

```ts
export type RelStatus = 'peace' | 'treaty' | 'tension' | 'war' | 'truce';

export interface Relation {
  trust: number;          // -100〜100
  status: RelStatus;
  since: number;          // この状態になった tick
  pacts: Pact[];          // 有効な協定
}
// world.relations[a][b]：N×N（非対称。相手への評価は国ごとに違う）

export interface Pact {
  kind: 'trade' | 'nonaggression' | 'water';
  until: number;
  params: Record<string, number>;   // 例：水利協定の最低流量
}
```

**信頼値を動かすもの**

| 増える | 減る |
| --- | --- |
| 貿易の継続、協定の履行、救援（食料の贈与） | 国境の摩擦（領土拡張で隣接）、**上流のダムで流量が減る**、協定違反、宣戦、禁輸 |

**外交の行動**（プレイヤーとAIで共通）

| 行動 | 内容 |
| --- | --- |
| 通商協定 | 交易の開始。期間と条件つき |
| 不可侵条約 | 期間中は宣戦できない（破ると信頼値が大きく下がる） |
| 水利協定 | 上流国が、下流国へ最低流量を保証する。見返りに富や食料を受け取る |
| 宣戦 | 開戦理由（casus belli）を必ず記録する |
| 停戦・講和の提案 | 条件（割譲・賠償・水利・通商）を添える |
| 贈与 | 食料・富を渡して、信頼値を上げる |

提案は `world.proposals` に積み、相手が数年以内に応答します。AIは、利得と信頼値と性格で受諾を判断します。**同盟は今回は入れません**（4か国では組み合わせが複雑になりすぎるため）。

### 22.3 貿易

**資源の追加**：鉱石を加え、資源は食料・木材・鉱石・富の4つにします。山岳（標高・傾斜が大きいセル）が鉱石を産みます。これで、山の国と平野の国が補い合う関係が、地形から自然に生まれます。

**取引の仕組み**（毎年1回、協定ごとに実行）

1. 各国の**余剰と不足**を、資源ごとに計算する（需要 − 生産と備蓄）。
2. **価格**：`価格 = 基準 × (需要 / 供給)^0.5`（上下限つき）。
3. 輸送コスト：交易路（§8.4 の経路探索を再利用）の費用 × 距離。川の下りは安く、海は港どうしが安い。
4. **取引が成立する条件**：国Aの余剰と国Bの不足があり、`価格差 − 輸送コスト > 0` であること。両国に利益がある範囲で、交易路の容量（道路の強さと港の容量の小さいほう）まで実行する。
5. 代金は富で精算し、貿易収支として記録する。

**禁輸と依存度**：戦争や敵対では、交易路が止まります。特定の国への食料の依存度が高いと、**禁輸が致命傷になります**。この依存度を、災害への強さ（§22.6）の評価に入れます。

**保存則**：輸出量の総和 ＝ 輸入量の総和（輸送損失を除く）。テストで確認します。

### 22.4 戦争

兵士を1人ずつ動かさず、**国境セルの押し引き**として抽象化します。作品の主題は地理なので、地形が勝敗を決めることを見せる設計です。

**軍事力**

```ts
export interface Military {
  troops: number;        // 兵力（人口から動員）
  equip: number;         // 装備（鉱石で向上）
  morale: number;        // 士気（戦争疲弊で低下）
  mobilization: number;  // 動員率 0〜1
}
```

```text
戦力 = 兵力 × 装備係数 × 士気 × 補給
補給 = LUT(首都・集落から前線までの経路コスト)    （道路があると短くなる）
```

**戦闘の解決**（戦争中は毎 tick、国境セルの対だけを処理。計算量は国境の長さに比例）

- 攻撃側の戦力と、防御側の戦力を、セル対ごとに比べる。
- **地形補正**：防御側が高地にいるほど有利。川を渡る攻撃は不利。森は守りに有利で、進軍が遅い。要塞（建設行動）は守りを強める。
- 押し勝った側が、隣接セルを**占領**する（`owner` を実効支配として変える。正統な領有権は別に持つ）。
- 占領地の集落は降伏する。略奪として一部の資源が移り、人口が減る。
- 乱数は、戦争ごとのPRNG（seed から導く）を使い、決定論を保つ。

**自然への応答（因果）**

| 行動・出来事 | 自然への影響 |
| --- | --- |
| 焦土作戦 | 敵領の植生が減る → 侵食が増え、食料が減る |
| 軍需の伐採 | 森林が減る |
| 農地の放棄 | 食料が減り、復旧が遅れる |
| **ダム・堤防の破壊工作** | 下流が洪水になる（§8.5 の洪水モデルへ接続） |
| 戦争中 | 復旧・開発の行動に制限がかかる |

**経済と終結**：軍の維持費（食料・富）が毎年かかり、戦争が長引くと**戦争疲弊**で士気が下がります。終結は、講和（割譲・賠償・水利・通商の条件）、休戦（期間つき）、首都陥落のいずれかです。

**国は滅亡させません**：首都が陥落しても、大幅な割譲と賠償で終わらせます。プレイヤーが理不尽にゲームオーバーにならないようにするためです。

**表現の方針**：矢印と前線で表す抽象的な見せ方にし、流血や残虐な描写はしません。教育への展開を考え、AIの宣戦を止める**平和モード**も用意します。

### 22.5 AI国家の拡張

§21.5 の Utility AI に、外交と軍事の行動を加えます。

```text
開戦の評価 = 期待利得（水・農地・港・資源） − 戦争のコスト − 負けるリスク + 感情（信頼値）
×  性格（aggression）
```

- **同じ情報・同じ規則**：AIは、国境付近で観測できる範囲の情報だけで、相手の戦力を推定する（簡易な戦場の霧）。プレイヤーも同じ。
- **理由を必ず記録**：宣戦には、開戦理由（水不足・領土侵犯・報復・食料不足など）を付け、ログに出す。プレイヤーが「なぜ攻められたか」を読める。
- **前触れを見せる**：緊張が高まると、緊張度のゲージが上がり、動員の兆候が地図に出る。**突然の宣戦にはしない**。
- **戦争の連鎖を防ぐ**：戦争疲弊、戦争後のクールダウン、国際イベントの確率の上限を設ける。
- **難易度**：aggression の倍率、判断の頻度、予報の利用。平和モードでは宣戦しない。
- **負荷**：外交・貿易は年1回、戦闘は国境セルだけ。1 tick あたり3ms以内を目標にする。

### 22.6 発展度の再配分

戦争・貿易を入れたので、§21.6 の重みを次のように変えます。**軍事力そのものは加点しません**（軍拡競争を避けるため）。

| 指標 | 重み | 追加・変更点 |
| --- | --- | --- |
| 人口 | 15 | 20から減らす |
| 食料の安定 | 15 | 輸入を含める。依存度が高いと減点 |
| 経済 | 20 | 貿易収支・交易路の数を含める |
| インフラ | 10 |  |
| 環境の健全さ | 15 | 焦土や軍需の伐採で下がる |
| 災害・安全 | 10 | 災害への強さに、被害・占領の少なさを加える |
| 技術 | 10 |  |
| 外交 | 5 | 信頼値の平均、有効な協定の数 |

勝って領土を得ても、環境・経済・災害・安全の面で負担が残るので、**戦争が割に合うかどうかが、プレイヤーの判断の対象**になります。

| 5h 戦争 | 動員、国境セルの戦闘、地形補正、補給、占領、講和 | 高地の防御側が有利で、川渡りの攻撃側が不利。戦争が必ず終わる |
| 5i AIの外交・軍事 | 提案と応答、開戦理由、前触れ、連鎖の防止 | 宣戦に理由が付き、突然の宣戦がない |
| 5j 外交・戦況UI | 各パネル、レイヤー、通知 | 負けている理由が地形で説明される |
| 5k バランス調整 | 画面なしでAIだけを大量に走らせるシミュレータ | §22.11 の統計基準を満たす |

規模が大きいので、**設計と型は最初から入れ、実装は段階的に出す**進め方にします。各マイルストーンで、デモできる状態を保ちます。

| マイルストーン | 内容 |
| --- | --- |
| M5 | 内政と発展度のランキングが回る（5a〜5e） |
| M6 | 貿易が回る（5f・5g） |
| M7 | 戦争まで含めて完成（5h〜5k） |

`relations` と外交・軍事のOpの型は、Phase 5a の時点で定義しておきます。そうすれば、あとから足しても、データやURLの形式を壊しません。

**削り順（更新）**：①要塞・破壊工作などの戦争の細部 ②水利協定・贈与 ③道路・港・都市の階層 ④AI国数を3→2 ⑤気候の季節変化 ⑥熱的侵食 ⑦256²モード ⑧モバイルの最適化 ⑨英語表示。 **削らないもの**：水文、河川侵食と堆積、神アルゴリズム、発展度の比較、貿易、戦争の基本（動員・国境の戦闘・講和）、URL共有、因果ログ。

### 22.11 検証

- **戦争が必ず終わる**：AIだけの1,000試合で、戦争の平均期間と最長期間に上限がある。
- **地形の効果**：高地の防御側の勝率が、平地より高い。川渡りの攻撃側の勝率が、渡らない場合より低い。
- **貿易の保存則**：輸出の総和 ＝ 輸入の総和（輸送損失を除く）。
- **禁輸の因果**：食料を輸入に頼る国で、禁輸の後に食料の収支が悪化する。
- **ダム決壊の因果**：破壊工作の後に、下流の洪水が発生し、被害が出る。
- **公平性**：AIとプレイヤーが、同じ情報・同じ規則・同じコストで動く。
- **AIだけの統計**：戦争の頻度、平和な期間の長さ、勝敗の偏り、首都陥落の頻度が、目標の範囲に入る。
- **平和モード**：宣戦がゼロになる。
- **決定論**：プレイヤーのOpだけのURLから、外交・戦争を含めて同じ世界が再現される。

### 22.12 未決事項

- 戦争の表現は、矢印と前線の抽象的なものでよいか。
- プレイヤーの敗北条件：国は滅亡しないので、発展度の最下位や、一定年数後の順位で決めるか。
- 同盟を、後から足せる形にしておくか、完全に外すか。
- 上流のダムによる渇水を、**開戦理由として正式に扱う**か（本章では扱う前提）。

## 23. シナリオ・因果・検証レイヤー（data/ 拡張）

§1〜22 の層別モデルに加え、**層をまたぐ拡張データ**を `data/` に追加した。
「地形が違うだけで世界が変わる」を感覚ではなく実験として示すためのレイヤーである。

| ファイル | 役割 |
| --- | --- |
| `scenarios.json` | 比較実験用シナリオ。terrain.json のプリセット3世界に、雨陰の二重苦・大河文明・交易狭所など4世界を追加。目的・初期条件・期待される因果連鎖・評価指標・成功基準を定義 |
| `feedback.json` | 因果ループの定義。雨陰→土壌水分→収量→人口、氾濫→肥沃度→余剰→国家能力、飢饉→移住→緊張→戦争、灌漑→塩類集積→農地劣化など10本を trigger → effect → secondaryEffect → amplifier → observable で明示 |
| `events.json` | 外生イベント（火山噴火・疫病・技術革新・移住の波・気候変動・黄金時代）。確率・持続期間・効果・回復を定義。発生は seed から決定的にし、URL共有の再現性を壊さない |
| `policy.json` | 国家政策（灌漑・森林保護・備蓄・軍事費・道路・検疫・交易奨励・治水）。コストと副作用を持ち、AI は nations.json の性格に応じて選ぶ。政策予算は国庫の年25%まで |
| `observables.json` | 検証可能な観測指標（人口・食料・貿易・戦争など約45種）。単位と集計方法（セル/国家/世界）を明示。scenarios の評価・feedback の観測・events と policy の効果先はすべてここを参照する |
| `validation.json` | 上記を含む data/ 全体の検証ルール。`scripts/validate.py` が必須キー・単位・範囲・参照整合性を機械的に検査する |

### 23.1 データの依存関係

```
terrain.json ──┐
climate.json ──┤
economy.json ──┼─→ feedback.json（因果ループ）─→ observables.json（指標）
nations.json ──┤            ↑                        ↑
events.json ───┤      policy.json（介入）      scenarios.json（評価）
disasters.json ─┘
```

- **シナリオ**は地形・気候の初期条件と評価指標を選ぶ
- **因果ループ**は層をまたぐ波及を宣言的に定義する
- **イベント**と**政策**は因果ループの trigger / amplifier に介入する
- **観測指標**はすべての評価・検証の共通言語になる

### 23.2 実装時の取り決め

- JSON を書き換えたら `python3 scripts/validate.py` を通す（参照整合性が壊れたままのコミットを防ぐ）
- イベント発生・政策選択・戦争の因果ログは §22 の因果ログに追記し、「なぜ起きたか」を追跡可能にする
- シナリオ比較は同一 seed で行い、observables.json の指標時系列の差分（Δ）と比率を出力する
- 新しい指標・政策・イベントを足す場合は、まず observables.json に指標を定義し、validation.json の検証を通す

### 23.3 今後の拡張候補

- 感度分析: 降水較正・土壌肥沃度・輸送コストを±20%動かしたときの指標の変化を自動測定
- リプレイと比較UI: 「同じ世界で灌漑技術だけ変えたら何が変わるか」を保存・再生できる画面
- 検証の CI 化: push ごとに `scripts/validate.py` を走らせる GitHub Actions

## 25. 等高線の幾何検証（terrain.json contourRules）

手描き等高線はラスタライズ→制約付き緩和の**境界条件**になるため、交差・重なり・
標高の不整合があると地形が破綻する。実地形の等高線と同じ性質（同一地点が2つの
標高を持たない、入れ子は山か盆地のどちらか）をデータとして強制する。

### 25.1 発見した問題と修正

`mountainRange` プリセットに2つの問題があった:

1. **等高線の重なり**: 標高0.05の等高線の中間区間が、標高0.7の尾根と同じ頂点を
   辿っていた。同じセルに矛盾する標高が書き込まれ、`overlap: average` で
   意図しない中間標高（約0.375）の尾根になる
2. **等高線の交差**: 標高0.05の等高線と標高0.4の等高線が世界の両端で交差していた

**修正**: 尾根を北西から南東に走る斜めの稜線として描き直し、3本の等高線
（0.05 / 0.4 / 0.7）を互いに交差せず（最小距離0.129）、標高が外側から尾根に
向かって単調に上昇する構成にした。西風が尾根の北東斜面（風上）に地形性降雨を
もたらし、南西側（風下）に雨陰砂漠ができる（scenarios.json の記述も更新）。

### 25.2 検証ルール（validation.json + scripts/validate.py）

| ルール | 内容 |
| --- | --- |
| noSelfIntersection | 1本の等高線は自分自身と交差しない |
| noMutualIntersection | 異なる等高線同士は交差しない |
| minSeparationNormalized 0.04 | 異なる等高線の最小距離。ブラシ幅を最小グリッド（128²）で換算した半幅の和＋余白。近接しすぎると同じセルに書き込まれ平均化される |
| elevationOrdering | 標高は尾根に向かって単調。入れ子の閉ループは「内側ほど高い（山）」か「内側ほど低い（盆地）」のどちらか。混在は警告（カルデラ型）、標高が等しい入れ子はエラー |
| minVertexSpacing 0.02 | 隣接頂点の最小間隔。短い辺はラスタライズで潰れる |
| bounds [0,1] | 頂点は正規化座標の範囲内 |

意図的に壊したデータ（交差・範囲外・短い辺・重なり）で4種すべて検出できることを
確認済み。現在のプリセット3世界はすべて通過している。

### 25.3 手描きのためのツール

等高線を自分で描くときのために2つ用意した:

- `scripts/check-contours.py`: 1プリセット単位の即時チェック。ペアごとの最小距離・
  入れ子関係・交差を詳しく報告する。terrain.json 形式のほか、単体の試し描きファイル
  （`{"contours": [...]}`）も直接読める
- `docs/contour-guide.md`: 描き方の作法（外側から描く・平行に流す・距離の目安・
  失敗パターンと直し方）
